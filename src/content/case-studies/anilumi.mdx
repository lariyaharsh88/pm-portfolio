## Summary

[AniLumi](https://anilumi.in/) is an anime discovery site. It shows what's airing this week in your own time zone, builds watch-order guides for long franchises, and tells you where to watch each show. I built it solo in October 2026 and launched it on my own domain.

The most useful thing I learned came after launch. When I switched on proper analytics, about 80% of visitors were from South Asia and two-thirds were on phones. The most visited page was the Hindi dub list. I had built for a global fan, and the audience told me who it actually was.

## The problem

Anime fans keep asking the same few questions:

- What's airing tonight, and what time is that for me?
- I want to start *Naruto*. What order do I watch it in, and what can I skip?
- How long will it take to finish?
- Where can I legally watch it?

The answers exist, but they're spread across wikis, Reddit threads and streaming apps. Most anime sites are built for people who already know the scene. Newcomers end up with 20 tabs open.

<Callout type="insight">
Every one of those questions is a search people type into Google. If each answer is a fast, clear page, search does the distribution for me.
</Callout>

## What I built

<Figure src="/case-studies/anilumi/schedule.webp" alt="AniLumi weekly schedule showing 25 episodes this week with a bar chart by day" caption="The weekly schedule: every airing show with Japan time and the viewer's local time side by side." />

**1. A schedule in your time zone.** Anime air times are in Japan time, which confuses everyone outside Japan. The schedule shows both, with next-episode countdowns and a chart of the busiest days.

<Figure src="/case-studies/anilumi/watch-order.webp" alt="Naruto watch order page with core entries, extras and filler advice" caption="Watch-order guides are generated from franchise data, then improved with editor notes on filler and canon." />

**2. Watch orders built automatically.** I generate the order from franchise relationship data, so a new season shows up without anyone editing the page. On top of that, I wrote notes for 53 popular franchises: which episodes are filler, which films are canon, and where to start.

<Figure src="/case-studies/anilumi/anime-page.webp" alt="Anime detail page with score, binge time, where to watch and watch order" caption="Each show page answers the next question too: binge time, where to watch, and where it sits in the watch order." />

**3. One page per question.** Each show has pages for how long it takes to watch, a parents' guide, next-season news, cast and opening songs. These match the long-tail questions people search for, and they link to each other so one visit turns into several.

**4. Tools that keep people around.** A "what to watch tonight" picker, a binge planner, tier lists, a quiz and a personal watchlist. None of them need an account. The list is saved on the device, so there's no sign-up wall.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 15 (App Router), React, TypeScript | Server-rendered pages that Google can read, with incremental regeneration |
| Styling and motion | Tailwind CSS 4, Motion | Fast to build; animations kept transform-only so they don't hurt load speed |
| Data | Kitsu API, AniList GraphQL (Jikan as optional fallback) | Free, no-key catalogue; AniList fills in air times Kitsu lacks |
| Database | MongoDB Atlas | Ratings and community data, switched off cleanly when not configured |
| Hosting | Cloudflare Workers via OpenNext, R2 cache, Durable Object queue | Edge pages close to users in India; ~90 ms of server time per page needed the paid plan |
| Automation | GitHub Actions | CI tests, a monthly data refresh and cache warm-up after each deploy |
| Measurement | Google Search Console, Bing Webmaster Tools, Cloudflare Web Analytics | Search demand plus bot-free visitor numbers |
| Extras | Generated OG images, RSS and iCal feeds, embed widget | Every page shares well and can be followed |

## Architecture

1. **Fetch:** a single adapter talks to Kitsu and AniList, normalises the data and rewrites short-lived image links into stable ones.
2. **Render:** pages are built on the server and cached at the edge, then refreshed on a schedule (hourly for airing data).
3. **Fail safely:** if an upstream API is down, pages show a "temporarily unavailable" state instead of a 404, so search rankings aren't lost.
4. **Personalise on the device:** the watchlist and preferences live in the browser, so there's no account and no personal data on a server.

## SEO and growth strategy

- **One question, one page.** Each show gets pages for watch order, binge time, parents' guide, next season, cast and opening songs, all matching real searches.
- **Internal links turn one visit into several.** Every answer links to the next likely question.
- **Structured data, but only what's allowed.** Breadcrumbs and video schema are in; star ratings were removed because Google only allows ratings you collect yourself.
- **Two search engines from day one.** Bing turned out to drive the Hindi-dub audience.

## Key product decisions

<Callout type="decision">
**Two data sources, and fail gracefully.** Kitsu gives me the catalogue and AniList fills in air times that Kitsu is missing. When an upstream API went down during the build, I made the site show a "data is temporarily unavailable" state instead of a 404. A false 404 tells Google the page is gone, which would quietly destroy search rankings.
</Callout>

<Callout type="decision">
**Follow Google's rules even when they cost clicks.** I removed star ratings from the structured data because Google's policy only allows ratings you collect from your own users. The stars would have looked good in search results, but they weren't mine to show.
</Callout>

## Mistakes and what I learned

<Callout type="tradeoff">
**I moved hosts three times in ten days, and Google noticed.** AniLumi went from Vercel to Render to Cloudflare between 23 October and 2 November. During the moves, Google hit 316 pages that returned server errors. Its traffic dropped the same day, and it hasn't recovered yet. I can't prove the errors were the only cause, but the timing matches.
</Callout>

- **Lesson: pick the host before launch, and migrate behind a stable URL.** Test the new host fully, then switch DNS in one step. Never let crawlers see a half-moved site. A re-check of the failing pages is now running in Search Console.
- **Lesson: one search engine is not a strategy.** Bing kept sending visitors while Google traffic was down. I now submit every site to both on day one.
- **Lesson: don't trust the first dashboard you open.** My hosting dashboard showed 1.6 million requests; real visitors were a few hundred a day. I only plan from analytics that exclude bots.
- **Lesson: let users tell you who they are.** I built for a global anime fan. Bing queries and analytics both said "Indian viewer looking for Hindi dubs", so the roadmap now starts there.
