## TL;DR

Content arrived weekly in spreadsheets and was uploaded by hand. Structured data (colleges, courses, exams, cutoffs) went in through raw CSV uploads that created duplicates and broken pages. I led the build of a platform where **one validated data layer powers every page, tool and SEO surface**. It includes a CMS with validation and audit trails, templated pages, student decision tools, and technical SEO designed in from the start.

## Context

Students choosing a college move through **Discover → Explore → Compare → Evaluate → Decide**. Established players (Shiksha, Careers360 and others) already own this search space. A new entrant cannot win with more articles alone. It wins with **better-structured information, connected into journeys, at a scale that search engines can index**.

## The problem

<Compare before="~4 hours" after="~10 minutes" label="Content processing time per batch" />

- **Publishing was manual.** Articles were shared weekly in sheets and uploaded by hand. That meant delays, formatting errors, and dependency on a few people.
- **Data was unsafe at scale.** Direct CSV uploads created duplicate articles and malformed data, and nothing stopped bad data from going live.
- **Pages were islands.** Content, college data and tools weren't connected, so a student reading about an exam had no path to cutoffs, predictors or comparisons.
- **SEO was an afterthought.** With hundreds of thousands of potential URLs, crawl budget, canonicals, internal linking and performance had to be product decisions rather than post-launch fixes.

<Callout type="insight">
For an education site, **the structured data *is* the product**. Articles attract a visit, but cutoffs, comparisons and predictors are what students come back for and act on. If the data layer is wrong, every page built on it is wrong at scale.
</Callout>

## What we built

I owned discovery, competitor analysis, information architecture, CMS design, prioritization and technical SEO strategy, working with engineering, content, SEO and business teams.

**1. A CMS that is a product, not an admin panel.** It manages articles *and* structured data, with bulk uploads that pass format checks, duplicate detection and error flags **before** publishing.

<Callout type="decision">
**Validate before publishing, not after.** At 300K pages, fixing bad pages one by one doesn't scale. The system has to catch predictable errors before any user sees them.
</Callout>

**2. User-level activity tracking.** Every change records who changed what, and when. When something broke, we fixed the *process* that caused it, not just the page: **issue → trace → root cause → fix workflow → prevent recurrence**.

**3. One data layer, many experiences.**
- College data → college pages → comparison → evaluation
- Exam data → exam pages → calendar → cutoffs → predictor
- Course data → course pages → course finder → comparison

<Callout type="decision">
**Treat structured data as a shared platform layer.** Building each feature on its own copy of the data would have been faster for the first feature and much slower for every one after it.
</Callout>

**4. Student decision tools.** College and course discovery, side-by-side comparison, exam calendar, exam and college cutoffs, college predictor, course finder, mock tests, and a personal dashboard.

**5. Templated pages at scale.** **Data → template → page → internal links → search discovery → user journey.** New page types launched by adding data, not by writing pages.

**6. Technical SEO as architecture.** Crawlability, indexation rules, URL design, redirects, metadata, canonicals, schema markup, internal linking, sitemaps, robots.txt, and continuous audits. Performance was built into templates, not fixed at the end.

## Trade-offs

<Callout type="tradeoff">
**Page volume vs. page quality.** Templates can generate millions of thin URLs. We only generated pages backed by real data and a real student question, and we controlled indexation for the rest. The goal was useful pages, not more URLs.
</Callout>

<Callout type="tradeoff">
**Richness vs. speed.** Data-dense pages (tables, comparisons, cutoffs) are heavy. We held a performance budget of 75+ mobile / 90+ desktop on PageSpeed Insights even when that meant cutting UI elements. [TODO: give one concrete example of something you cut or deferred.]

<Callout type="tradeoff">
**Short-term traffic vs. long-term architecture.** Big URL and template migrations cause temporary ranking volatility. We accepted the dip for a structure that could scale.

## What I'd do differently

{/* TODO: these are suggested reflections. Keep only the ones that are true for you. */}
- **Plan migrations with a traffic-risk budget.** I would stage URL and template changes by section, with rollback criteria, instead of changing several SEO systems at once. Doing it that way would have made the dip smaller and easier to diagnose.
- **Instrument the funnel, not just sessions.** Sessions show discovery. I would track compare → predictor → lead conversion per page type from day one to prove which tools drive business value.
- **Kill weak page types faster.** Use engagement and indexation data per template to retire low-value pages sooner.

## If I built this today with AI

- **AI-assisted structured data entry.** Extract college, fee, cutoff and eligibility data from official PDFs and notices with an LLM using structured outputs, validated against the schema the CMS already enforces. A human approves anything with low confidence.
- **Content QA agent.** Flag outdated dates, contradictions with the structured data ("article says the fee is X, the data layer says Y"), and missing internal links before publishing.
- **Conversational predictor.** "Which colleges can I get with rank 12,000 in JEE Main?" answered from *our* cutoff data with citations, not from the model's memory.

**How I'd evaluate it:** field-level extraction accuracy on a labeled set of 200 documents, factual-consistency rate against the data layer, citation coverage, cost per page updated, and latency. The non-negotiable is that no AI-generated number goes live without passing the same validation a human upload would.
