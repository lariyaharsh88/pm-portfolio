## Summary

E-commerce has been built for humans clicking through pages. I built **Agent Store** for two shifts I think are coming: customers will send agents to shop, and small merchants will want an agent, not a team, running their growth experiments. The store exposes contracts instead of layouts, runs every experiment as a bandit that optimises profit, and logs every action any agent takes. Status: working demo with a deterministic optimizer; the Claude-planned optimizer path is built but awaits a live-key comparison. Source on [GitHub](https://github.com/lariyaharsh88/agent-store).

## The problem

1. **Customers will send agents to shop.** An agent can't reliably use a store built from visual pages and pop-ups. It needs structured discovery and a purchase API.
2. **Small merchants can't run experiments.** A/B testing needs traffic, analysts and patience. Most D2C stores leave their headline, pricing and shipping threshold unchanged for years.

<Callout type="insight">
If a store exposes the right tools, an AI agent can be its **customer**, and another agent can be its **growth team**. The bar is that every action the agent takes is safe, reversible and auditable. Without that bar, no merchant will switch it on.
</Callout>

## Users

- **Shopping agents**, and the people who send them. They need discoverable, structured APIs.
- **Merchants.** They want growth without hiring a growth team, and they want to stay in control.

## Options considered

<Options>
  <Option title="Fixed 50/50 A/B tests">
    The standard approach, but a small store takes weeks to reach significance on one test, and loses half its traffic to the loser the whole time. Rejected.
  </Option>
  <Option title="Optimise conversion rate">
    The obvious metric, and the wrong one for price tests: optimising conversion alone teaches the store to cut prices. Rejected as the objective for pricing.
  </Option>
  <Option title="Let the LLM act directly on the database">
    Fastest to build, impossible to audit, and one hallucinated price change ends the merchant's trust. Rejected.
  </Option>
  <Option title="Thompson-sampling bandits on profit, behind a single audited tool registry" chosen>
    Traffic shifts to winners while still learning. Price arms are weighted by unit profit. Every operator, human or agent, HTTP or MCP, goes through the same tools and the same log.
  </Option>
</Options>

## Key decisions

<Callout type="decision">
**Agents need contracts, not layouts.** Discovery is through `llms.txt`, an OpenAPI spec, `.well-known/agent.json` and schema.org JSON-LD on every product page. The HTML is for humans; the store is defined by its API.
</Callout>

<Callout type="decision">
**One tool registry for every channel.** The HTTP tool API, the MCP server and the built-in optimizer agent all call the same registry. One set of rules, one audit trail, whoever is operating.
</Callout>

<Callout type="decision">
**The product must work without the model.** With an API key, Claude plans the optimizer's moves. Without one, a deterministic policy runs through the same tools. That keeps the system testable and makes the LLM's contribution measurable rather than assumed.
</Callout>

## How I validated it without real traffic

I built a shopper simulator with **hidden** preferences: price elasticity by category, sensitivity to headlines and CTAs, and customer segments. The store and the optimizer never read that file, so they have to *discover* those preferences through experiments. If the conversion chart on the operator console goes up, the system learned something real about the simulated market.

## Results

One run on a fresh database, deterministic optimizer, 400 simulated shoppers per cycle.

| Stage | Sessions | Orders | Conversion | Revenue / session |
|---|---:|---:|---:|---:|
| Baseline, no optimizer | 400 | 84 | 21.0% | $33.29 |
| Cycle 1: four experiments launched | 400 | 71 | 17.8% | $26.51 |
| Cycles 2–3: bandits collecting data | 800 | 204 | 25.5% | $38.07 |
| Cycle 4: headline winner applied, P(best) 95% | 400 | 108 | 27.0% | $42.15 |
| Cycle 5: restock, winner holding | 400 | 106 | 26.5% | $41.63 |

<Compare before="21.0%" after="26.8%" label="Conversion rate: baseline vs. the winning headline arm at conclusion" />
<Compare before="$33.29" after="$41.89" label="Revenue per session: baseline vs. the two cycles after the winner was applied" />

- The optimizer launched four experiments in cycle 1 (headline, CTA copy, free-shipping threshold, a price raise on one product), waited two cycles while the bandits collected data, then concluded the headline test: "Free shipping on orders over $75" won at a 26.8% rate with 95% probability of being best, and was applied to the store automatically.
- Cycle 1 dipped below baseline. That is the cost of exploration: new arms get traffic before they are proven. Bandits shrink that cost compared with a fixed split, but do not remove it.
- Every one of the 13 tool calls across the five cycles is in the action log with the agent's name, inputs and outcome.

<Callout type="result">
**What this proves and what it does not.** It proves the loop works end to end: traffic in, experiments launched, a winner found and applied, revenue per session up about 26% against baseline. It does not prove a real store would see that lift. The simulator's preferences are my assumptions, and one run is one run. The live-key test of the Claude optimizer against this policy, on the same seeds, is the next experiment.
</Callout>

## Risks I designed for

- **Runaway pricing.** Price arms are bounded and weighted by unit profit, so the bandit cannot "win" by giving the product away.
- **Agent mistakes.** The audit log, an insights memory agents write to and read first, and a human-visible operator console.
- **Model unavailability.** The deterministic fallback runs through the same tools, so the store never depends on the model being up.
